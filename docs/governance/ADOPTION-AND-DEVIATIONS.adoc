= Adoption and Deviations

Upstream: `https://github.com/hyperpolymath/standards` at `2ccc38eaaf8787034ed099e0b72c9ca8b85dc563`.

== Adopted now

* A2ML placement convention: universal `0-AI-MANIFEST.a2ml` at root; ordinary metadata under `.machine_readable/`.
* Descriptile naming for new metadata.
* Separation of authority, profiles, local bindings, and evidence.
* Evidence-status honesty: draft, designed, assumed, tested, audited, and proven are not interchangeable.

== Proposed adoption

The Hyperpolymath constitutional district on `constitution/estate-foundation` is under review. Its authority, assurance, contribution, exception, challenge, and tension principles are proposed for adoption after upstream merge and a pinned-hash update.

== Not automatically applicable

Language/toolchain profiles, release requirements, MAA profiles, and implementation-specific standards apply only when a project binding selects them. Organisational distinction alone does not create a Metadatastician standards fork.

== Deviations

No substantive deviation is *authorised* in this initial draft. Existing repositories may predate current metadata and terminology conventions; that is migration debt, not an implicit deviation. Each exception requires scope, authority, reason, containment, evidence status, and review date.

That sentence is about authorisation, and it stays true. What follows is a record
of three deviations that *exist in merged history or in the working tree* as at
2026-09-28. Recording a fact is not authorising it: each is stated with the six
fields this section requires, and each is marked for the owner to ratify,
reverse, or rule on under `CHANGE-PROCEDURE.adoc`. They are written down because
an unrecorded deviation is indistinguishable from an unnoticed one, and two of
the three were found only by reading the merged diff against the rule the
repository states about itself.

=== D-A — `actions.lock` was edited without `gh actions-lock`

*Scope.* One file, `.github/workflows/actions.lock`, in PR #42 (squash-merged as
`7276ec80e5`, 2026-09-28T00:09:34Z). The measured diff adds three entries and
re-sorts two: `ci.yml`, `estate-sweep-watchdog.yml` and `lock-sync-gate.yml` gain
empty lists (`[]`), and `labels.yml` / `label-triage.yml` move to alphabetical
order. No `dependencies:` record was added, removed or altered, so no claim about
a resolved commit, ref or `owner_id` was fabricated by hand.

*Authority.* None exists as a ruling. The change is in merged history because the
repository owner squash-merged the PR that carried it, which is acceptance in fact
and not a decision about this rule. The file's own header says "Do not edit by
hand; run `gh actions-lock` to update", and this document quotes the estate rule
as "`actions.lock` — must never be hand-edited or reformatted". Both were
contradicted.

*Reason.* The sanctioned tool could not be run: `gh extension install
github/gh-actions-lock` fails in the authoring environment on the release-asset
CDN host (raw output and diagnosis in `CI-CD-COVERAGE.adoc`). The three workflows
in question carry no `uses:` at all, by design, so their entries assert nothing
that requires resolution. Leaving them unlisted instead would have made the
lock-sync gate's "not onboarded" NOTE ambiguous between *has refs nobody locked*
(the real gap: `codeql.yml`, `oikosbot.yml`, `scorecard.yml`,
`secret-scanner.yml`) and *has no refs to lock* (nothing to do).

*Containment.* An empty entry is falsifiable offline and is falsified by this
repository's own gate: `scripts/check-lock-sync.sh` reads the YAML with a parser
and fails (exit 1) if a listed path disagrees with the workflow in either
direction, so a wrong `[]` cannot survive a run. `tests/mutation-score-test.sh`
mutates that gate until it stops checking and proves the corpus notices. The
dangerous half of the lockfile — dependency records asserting reachability — was
not touched and must not be: that claim cannot be verified without the tool.

*Evidence status.* Tested locally (gate exit 0; `git status` shows the lock
untouched by any subsequent work) and observed on a runner: the merge push ran
`Lock Sync Gate` to success (`36361142025`) and every uses-free workflow started.
Not audited.

*Review date / re-arm.* The probe that carried this trigger was retired
2026-09-29 with its question answered by the CI-Health Sweep's own runner step
(`gh extension install github/gh-actions-lock --pin v0.1.6` completes on
`ubuntu-latest`; recorded in `CI-CD-COVERAGE.adoc`). The re-arm stands in a
stronger form than the probe could offer: on the first live B-LOCKFIX repair
whose generated lock passes `check-lock-sync.sh` and `check-lock-pins.sh
--offline` on the runner, take only `actions.lock` from the result and confirm
the three entries survive as the tool writes them — which either ratifies this
deviation retrospectively or shows the hand-made shape was wrong. If the owner
prefers, revert the three entries now: the gate reports them as NOTEs, not
failures, so nothing breaks.

=== D-B — `ci-health-sweep.yml` carries a mutable tag, not a SHA pin

*Scope.* One line: `- uses: actions/checkout@v7.0.1`. Every other workflow here
is SHA-pinned.

*Authority.* Same as D-A: merged in #42 by the owner, no separate ruling.

*Reason.* This is the inverse of the incident that D-A sits next to, and the two
must be read together. PR #40 (`5d9e8b8088`, 2026-09-23) *hardened* this line
from `@v7.0.1` to `@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1` — the very
commit the lock already resolved that tag to — without regenerating the lock.
Because the lock matches on the ref string recorded under a workflow's own path,
GitHub refused to start the run: four consecutive scheduled sweeps
(2026-09-24 … 2026-09-27) produced `startup_failure` with zero jobs. #42
restored the tag the lock records. The deviation is therefore *deliberate*: with
the lock unregenerable, the pinned form is the broken one and the mutable form is
the one that runs.

*Containment.* The tag is recorded in the lock with its resolved commit
(`sha1-3d3c42e5…`) and `owner_id`, and `scripts/check-lock-pins.sh` verifies that
record; the exposure is the ordinary mutable-tag risk (the ref could move
upstream), not an unverified pin. The gate that keeps YAML and lock in agreement
runs on every PR and push.

*Evidence status.* **Proven.** The next scheduled sweep ran as
`36379748097` at 2026-09-28T04:55:58Z and *started*: step 2,
`Run actions/checkout@v7.0.1`, succeeded — the lockfile resolving this exact
mutable tag to its recorded commit, end to end, on a runner — and the job ran
17m54s. Gates also exit 0 locally and `Lock Sync Gate` succeeded on `main`
(`36361142025`). The sweep still failed in that run, at step 3, for an unrelated
reason (one empty repository in scope, initially misdiagnosed as its PAT's scope
and corrected on 2026-09-29; see `CI-CD-COVERAGE.adoc`), which does not bear on
this deviation: the ref resolved, and that is the whole claim D-B makes.

*Review date / re-arm.* Immediately after the lock tool is proven runnable:
regenerate, then convert this line to the full SHA and confirm
`check-lock-pins.sh` still passes. This deviation should be the first one closed,
because it is the one that is actively costing pinning coverage.

=== D-C — `oikosbot.yml` runs a container image pinned by digest, not by version tag

*Scope.* One line: `ghcr.io/hyperpolymath/oikos@sha256:31d12c9139f13a58f7581008d888e4bb4fa8d9120091137e2ac652b3b5a6b661`
(OCI index of `sha-9df7a29`, which `development` also names), invoked by
`docker run`. Present in the `:latest` form since at least 2026-07-28
(`2143f7e74d`); pinned by digest 2026-09-29 (`cc9b731d…`, then `latest`);
re-pointed 2026-10-05 because that build could not start (see below).

*Authority.* None — originally the clearest case of an unnoticed deviation
rather than a chosen one: it survived because no gate in this repository reads
image references inside `run:` blocks — the pinning gates read YAML `uses:`
values, and a `docker run` string is opaque to them. The 2026-09-29 re-point
brings it under deliberate, recorded management without changing that gate
blind spot.

*Reason.* The file's own history records the shape of the gap: "The former
`ghcr.io/hyperpolymath/oikos:v2.0.0` pin referenced a tag that never existed on
the package." On 2026-09-29 the claim behind the choice was verified directly
rather than quoted: the package's public package page
(hyperpolymath/oikosbot → Packages → oikos) shows *no version tags at all* —
upstream pushes `latest` plus `sha-<commit>` tags from its CI — while `latest`
did resolve, sharing digest `sha256:cc9b731d…` with `sha-2f47a61` at read
time. A tag that another repository's CI overwrites is not a pin; a digest is
what the registry can be asked to verify. The digest is therefore pinned with
its provenance recorded in-file, and the workflow prints the registry-resolved
RepoDigests line so the job log carries the exact bytes that ran. The registry
counterexample stands on two legs, both dated 2026-09-29: the tag list is
digest-shaped (`latest`, `sha-<commit>`, no `v*`), and no semantic-version tag
exists to name.

*Cause of the red run, established 2026-10-05.* Two defects, in order. (1) The
`cc9b731d…` image (`sha-2f47a61`) was built with `rust:1-slim` — Debian Trixie,
glibc 2.41 — and copied onto a `debian:bookworm-slim` runtime (glibc 2.36), so
the binary died at exec with `GLIBC_2.38' not found` / `GLIBC_2.39' not
found` (PR #58 run `37358546903`). Upstream fixed the Containerfile in
hyperpolymath/oikosbot `9df7a29` (#110, both stages Bookworm) and stopped
moving `latest` (`publish-image.yml`: `latest=false`), so `latest` is frozen at
the broken build. (2) With a working image, `.oikos.yml` listing `idris`, `zig`,
`haskell` or `typescript` makes the run exit 2 — "no check performed:
unsupported configured language" — again with no SARIF; the analyzer supports
`rust`, `javascript`, `python` only. Both were reproduced locally with podman
against this repository's `main` and the fix (new digest + supported languages)
produced a valid SARIF and exit 0.

*Containment.* Weak, and stated as weak: the job runs with
`permissions: security-events: write, contents: read`, `--user "$(id -u):$(id -g)"`,
a read-only-mounted workspace by convention rather than enforcement, and its SARIF
upload is a separate step. The digest pin removes the *moves-under-you* half of
the exposure — `latest` re-pointing silently — but the image content itself is
exactly as much of an upstream product as it was. The run is *also* the one
failing on `main` (`36361141992`, `36398030720`: analysis produces no
`results.sarif`, upload then fails for want of its input); the digest pin does
not claim to cure that failure, which lives inside the image and is upstream's
to fix or absorb — it makes the failure attributable by making every run
byte-reproducible.

*Evidence status.* Partially measured, stated as such: the digest's validity
read off the public package page (2026-09-29); the analysis failure's root
cause not established here. No gate covers image references in `run:` blocks;
no test asserts anything about this pin.

*Review date / re-arm.* Two triggers, whichever comes first: the upstream
package publishes a real version tag, at which point pin it by digest of that
tagged release; or a gate is added that reads container image references in
`run:` blocks and requires a digest. The second is the better fix, because it
closes the blind spot rather than the instance — and it should be proposed
under `CHANGE-PROCEDURE.adoc`, not added unilaterally, since it changes what
every workflow in this repository must satisfy.

== Sequenced upstream adoptions (in force upstream, not yet actionable here)

Upstream sometimes rules a standard *before* the estate can comply with it, and
sequences the compliance work behind a proof so that a half-built gate is not
mistaken for a working one. Those rules are recorded here so that no repository
in this estate silently invents its own answer.

=== Y-1 — gates read YAML with a parser (IN FORCE, adopted here now)

`hyperpolymath/standards` `3-practice/YAML-POLICY.adoc`, ruled 2026-09-22:
*any gate, check script, audit or census that needs a value out of a YAML file
MUST obtain it with `yq`; reading YAML with `grep`, `sed`, `awk` or a regex is
forbidden in gate code.*

Status here: *adopted*. `scripts/lib/yaml.sh` is the single reader. It resolves
a document with a real parser and hands canonical JSON to `jq`, and there is no
text-reading fallback in it. Every gate in `scripts/` that touches YAML uses it.

*Recorded deviation, narrow.* Y-1 names `yq`. This repository prefers `yq` and
uses it when present, but falls back to another *real parser* (`ruby`, then
`python3`+PyYAML) when it is not, following the precedent in upstream's own
`tools/policy/check-workflows-parse.sh`, which falls back to `ruby`. The reason
is operational: GitHub's `ubuntu-latest` does not ship mikefarah `yq`, and this
repository's gates must not be the reason a runner cannot start. The deviation
is *not* extended to text readers — that remains forbidden, because a
line-oriented reader giving a confident answer about a structure it cannot see
is the defect class Y-1 exists to end. Re-arm trigger: when a pinned `yq` is
available on the runner image or via a pinned install step that does not add a
`uses:` to a uses-free gate, drop the fallbacks and require `yq`.

=== Y-2 / Y-3 — `yq` for writing, and KYAML as the authoring dialect (SEQUENCED)

*Status: nothing in this repository is out of compliance, because neither rule
imposes anything today.* Y-2 (`yq` for writing) and Y-3 (KYAML) are both gated
on a comment-preservation proof, and Y-3's scope is an owner ruling that has
deliberately not been made. The upstream sequence is:
