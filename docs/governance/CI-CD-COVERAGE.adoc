:toc:

What continuous integration and delivery actually runs in this repository, what
it deliberately does not, and what is left to do elsewhere. The reference is the
estate's
https://github.com/hyperpolymath/standards/blob/main/CICD-WORKFLOW-CATALOG.md[CI/CD
Workflow Catalog]; the catalogue's instruction is to *call* reusable workflows
from `hyperpolymath/standards` and *copy* only the non-reusable ones.

Measured 2026-09-28, across two merges to `main` — pull request #42 at 00:09 UTC
and pull request #44 at 08:33 UTC. "Starts" means the run was created and
executed; a `startup_failure` is not a red check, it is a check that never
existed. Every run id, count, step conclusion and annotation quoted below was
read from the API or the run page on that date; nothing here is inferred from a

== The one structural rule in this repository

*A gate that must survive a lockfile fault may not carry a `uses:`.*

GitHub resolves a workflow's `uses:` refs through `.github/workflows/actions.lock`
at run creation. A ref the lock does not record under that workflow's own path
makes GitHub refuse the run — `startup_failure`, zero jobs, no log, nothing in
REST or GraphQL. So a workflow whose job is to *detect* that fault cannot depend
on the mechanism it detects. `ci.yml`, `lock-sync-gate.yml`,
`estate-sweep-watchdog.yml`, `labels.yml`, `label-triage.yml` and the temporary
`zz-probe-actions-lock.yml` therefore check out by calling `git` inside a `run:`
step. Do not add a `uses:` to them.

== A detector that measures correctly and describes it wrongly

The watchdog's first run is a small case study, and it is recorded here because
the failure mode is the same one that made the original outage take four days to
diagnose: *a correct measurement wrapped in an incorrect sentence.*

What it measured at 07:45:39 was right. The sweep's last **success** was
2026-09-20T04:48:25Z, more than 26 hours old, so the rolling estate report on
issue #30 is stale; the latest run concluded `failure`. It fired on staleness of
the last success — not on a startup failure, because there wasn't one.

What it then said was wrong. It titled issue #43 "🩺 CI-Health: sweep is not
running", headed the body "the sweep itself is not running", and spent the whole
body explaining the two causes of `startup_failure`. The sweep *had* run, for
eighteen minutes, and had checked out successfully through the very lockfile the
body told the reader to go and suspect. Anyone following that issue would have
re-derived the wrong diagnosis a second time.

A second defect was found while reading the code to fix the first: the body
promised "This issue closes itself on the next healthy sweep run", and **no code
path ever closed it**. The healthy branch printed "sweep is healthy; nothing to
report" and exited before any issue handling, so #43 would have stayed open
forever after the sweep recovered. A promise a workflow does not keep is worse
than no promise, because it teaches people to ignore the workflow.

Both are fixed in #44, with the trigger calibration deliberately left
alone — *when* it fires was right, only *what it says* and *whether it cleans up*
were wrong:

* The title becomes "🩺 CI-Health: estate report is stale", which is true in
  every case that fires it (no success ever, success too old, or a run that
  failed to start) and asserts no cause.
* The observed state is derived from the measurement: *did not start*, *started
  and then failed*, *succeeded but the success is older than the horizon*, or
  *no run history at all*.
* The guidance branches on that state. A run that started is told to compare
  `started_at` and `completed_at` — minutes means the script ran, seconds means
  it died at its first command — and is pointed at the honest-refusal guard and
  the token-scope requirement first. The two `startup_failure` causes are shown
  only when the run actually failed to start.
* The healthy path now closes the issue, requiring both a fresh success *and*
  that the newest run is that success; a fresh success with a newer failure on
  top of it is reported as "the published report is one run behind" rather than
  silently closed.
* Because the title is also the search key for the rolling issue, the previous
  wording is still searched for and any issue found under it is renamed, so
  changing the title cannot orphan #43 and open a duplicate every run.

Verification, since a run pushed by the authoring agent is refused (cause 2) and
cannot test it: the step's script was extracted from the YAML *with a parser*,
checked with `bash -n`, then executed against the live API and against four
synthetic run histories — `startup_failure`, fresh `success`, `failure` over an
older success, and no runs at all. All four exit 0 and take the correct branch,
with issue mutations intercepted. That run also caught a bug the author
introduced while rewriting the file (a jq path, `[.workflow_runs][0]` where
`[.workflow_runs[]][0]` was meant), which is the argument for executing the
extracted script rather than reading it.

=== The commit that caused the four-day outage, and why it is a trap

Cause 1 is now traced to a specific commit rather than described as "drift", and
the mechanism is worth more than the incident.

PR #40 (`5d9e8b8088`, merged 2026-09-23T11:10:18Z, "Fix/deadlock script exit
code") made exactly one change to `ci-health-sweep.yml`:

----
-      - uses: actions/checkout@v7.0.1
+      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
----

That is a *hardening* change — mutable tag to immutable SHA, the estate's own
pinning policy, applied by hand. It did not touch `actions.lock`, which at that
commit recorded, for that workflow path, the entry
`'actions/checkout@v7.0.1'` with dependency
`ref: 'v7.0.1'`, `commit: 'sha1-3d3c42e5aac5ba805825da76410c181273ba90b1'`.

Read those two facts together and the trap is visible: the SHA the YAML was
changed to name is *byte-for-byte the commit the lock already resolved `v7.0.1`
to*. The pin was not merely equivalent in intent, it was identical in effect —
same action, same commit, same owner, a strictly better supply-chain posture —
and it killed the workflow at startup for four consecutive days, because the lock
matches on the **ref string recorded under that workflow's path**, not on the
resolved commit. `3d3c42e5…` is not a ref the lock records for
`ci-health-sweep.yml`, so GitHub refused the run: zero jobs, no log, no
annotation, nothing in REST.

The next scheduled sweep ran at 04:47 UTC on 2026-09-24, eleven hours after that
merge, and was refused. So were the next three. The detector the estate built to
find CI failures was itself the failure, and a `startup_failure` produces no red
square for a required check to hang on — which is why nothing on any dashboard
went red, and why the incident was found by a human reading a stale board.

Three consequences, each of which is a rule rather than a story:

. *Doing the right thing to a pin is not safe on its own.* Any tag-to-SHA
conversion, Dependabot bump or manual re-pin must be accompanied by a lock
regeneration, or it is an outage wearing a security improvement's clothes. Where
the lock cannot be regenerated — as here, and as in every sandboxed agent session
in this estate — the safe move is the counter-intuitive one: leave the readable
tag the lock records, and record the deviation. That is what #42 did, and it is
why `ci-health-sweep.yml` still says `@v7.0.1`.
. *A gate must check both directions.* "Does every ref in the YAML appear in the
lock?" catches this. So does "does every lock entry still have a ref?", which
catches the orphaned entry a fix leaves behind. `scripts/check-lock-sync.sh`
checks both, and `tests/mutation-score-test.sh` proves each direction is load-
bearing by mutating the gate until it stops checking.
. *The watcher needs a watcher.* `estate-sweep-watchdog.yml`, added by #42,
exists precisely because a `startup_failure` is invisible to every mechanism that
reads check conclusions. Its first scheduled run is 07:17 UTC on 2026-09-28 and,
like the sweep's repair, it is unproven until it happens.

The separating measurement is worth stating precisely, because it is what makes
the two causes non-negotiable rather than merely plausible. In the last 100 runs
the coding-agent app has exactly six successes, and all six are `dynamic`-event
runs (`PR #42`, GitHub-managed CodeQL analysis) — *not one repository workflow
file has ever started for that actor*. Meanwhile the same app-adjacent content
starts fine for a human actor. The sharpest instance is a three-minute window on
2026-09-28, on one pull request, with one lockfile:

* 00:03 — commit `3c6fd1c64e` was pushed through the GitHub web UI by the
  repository owner (a Copilot Autofix suggestion). Actor `hyperpolymath`. All
  five repository workflows *started*: runs `36360781724` (Lock Sync Gate,
  success), `36360781734` (CI, failure inside the job), `36360781742` (CodeQL),
  `36360781695` (OikosBot), `36360782233` (Secret Scanner, success).
* 00:06 — commit `55e0ae2b6d` was pushed by the coding-agent app. Actor
  `arena-ai-coding-agent[bot]`. All five were refused: `36360948079`,
  `36360948616`, `36360949176`, `36360949721`, `36360950443`.

`compare/3c6fd1c64e…55e0ae2b6d` touches `ci.yml`, `lock-sync-gate.yml`,
`estate-sweep-watchdog.yml`, `detect.sh`, `sweep.sh` and this document. It does
**not** touch `actions.lock`, `codeql.yml`, `oikosbot.yml`, `secret-scanner.yml`
or `labels.yml`. So for CodeQL, OikosBot and Secret Scanner the file content was
byte-identical three minutes apart, the lockfile was identical, and the only
variable that changed was the actor. That is as close to a controlled experiment
as an incident leaves behind.

The consequence is worth stating plainly, because it cost this estate real time:
a sweep that classifies every `startup_failure` as lock drift will report a
settings problem as a YAML problem forever. Files can be read, regenerated and
re-checked indefinitely and the board will not move, which is exactly how this
class survived four rolling issues. `detect.sh` splits them by actor —
`B-LOCKFILE`/`B-BADPIN` for the file-readable causes, `B-ACTOR` for the settings
cause — and `sweep.sh` reports `B-ACTOR` as owner-actionable rather than
attempting a repair.

*Standing request to the owner, unchanged and still blocking:* the org or
repository Actions policy must permit the coding-agent app to trigger workflows,
or every push made by an agent — including the ones that carry fixes — produces a
wall of `startup_failure` and no runnable CI. Until then no branch in this
repository can be verified by a green run of its own, and verification has to be
static (schema-valid lock, gates green locally, run ids cited) plus whatever the
owner's own triggers produce on `main`.

One cheap workaround exists and is worth knowing: a refused run can be re-run
from the UI by a permitted actor, and a re-run executes as the person who
clicked, using the workflow file from that run's commit. That is how the
`gh actions-lock` probe below can be answered without merging anything.

== Blockers, with re-arm triggers

*The lock cannot be regenerated in the authoring environment.* `gh actions-lock`
is the estate's canonical generator and it is not obtainable there. Measured
2026-09-28, raw:

----
$ gh extension install github/gh-actions-lock
failed to download asset linux-amd64: Get
"https://release-assets.githubusercontent.com/github-production-release-asset/…": EOF

$ gh actions-lock --version

/home/user/.local/share/gh/extensions/gh-actions-lock/gh-actions-lock: no such file or directory

$ curl -sSL -o /tmp/yq https://github.com/mikefarah/yq/releases/latest/download/yq_linux_amd64
curl: (35) OpenSSL SSL_connect: SSL_ERROR_SYSCALL in connection to
release-assets.githubusercontent.com:443
----

The diagnosis this supports is narrower and more useful than "the tool is
missing": the extension's *metadata* is reachable — `GET
/repos/github/gh-actions-lock/releases/latest` answers `v0.1.6`, published
2026-07-28, asset `linux-amd64`, 11268280 bytes — and its *source tree* clones
fine (`git ls-remote https://github.com/github/gh-actions-lock` succeeds). Only
the release-asset CDN host fails, and `proxy.golang.org` fails the same way, so
building from source is not a route either (`go` is absent regardless). This is a
sandbox egress restriction on one class of host, not a missing tool and not a
missing licence. It matters more than convenience: the lock is the file whose
hand-editing caused the four-day sweep outage, and a hand-built replacement has
already been shown to produce a file GitHub rejects wholesale — every workflow
in the repository then fails at startup, including uses-free ones. The interim
answer is unchanged: modify nothing in the lock, and make the workflows agree
with it.

*The runner-side answer is pending, and it is one click away.*
`.github/workflows/zz-probe-actions-lock.yml` is a temporary, uses-free,
read-only probe that installs the extension on a GitHub runner, prints
`gh extension list`, the real `--help` flag surface, the result of
`gh actions-lock --verify` (which is `--rescan --no-fix`, so it writes nothing),
and then — in a throwaway copy under `/tmp`, never in the repository — what a
full regeneration would change. It checksums the real lock before and after and
prints `git status --porcelain` as the backstop, so "read-only" is demonstrated
rather than asserted. While an agent pushes it, it is refused like everything
else; the answer comes from a permitted actor either re-running the refused run
or dispatching the workflow once it is on the default branch. Its `--verify` semantics were read out of the
extension's source at `v0.1.6` (`cmd/gh-actions-lock/run.go:93`: "Full
re-verification of every pin (equivalent to `--rescan --no-fix`)") and its exit
contract from `cmd/gh-actions-lock/root.go:30` (0 clean, 1 blocking findings,
2 tool failure — bad flag, IO error, network failure, malformed lockfile), so the
probe's output will be interpretable when it lands.

Reading that source also surfaced something this repository did not know it was
duplicating. The tool already ships the exact check `scripts/check-lock-sync.sh`
hand-rolls: `--verify-local` performs "a zero-network static check: every action
ref in scanned workflows must have a corresponding lockfile entry. No auth, no
resolution, no reachability — ideal for pre-commit hooks." Two consequences,
both worth an owner decision rather than a unilateral change here. First, this
repository's gate is not redundant busywork — it reads *job-level* refs that
`--verify-local` is documented to miss, and it checks the reverse direction
(lock entries with no ref), so it is a strict superset for this repository's
shape. Second, once the tool is obtainable on a runner, `--verify-local` becomes
the cheapest possible cross-check to run alongside the hand-rolled gate, and any
disagreement between them is itself a finding.

**Re-arm trigger:** when `gh actions-lock` is proven to run on a runner,
regenerate the lock in a scratch copy, take *only* `actions.lock` into the
repository, prove with `scripts/check-lock-pins.sh` that no pin moved and with
`git diff --name-only` that nothing else did, then re-pin every workflow to full
SHAs and re-run the gates. The scratch-copy discipline is not caution for its own
sake: fix mode is documented to rewrite workflows as well as the lock, and
`metadatastician/burble#224` measured it appending duplicate management banners
to 27 files and de-pinning bare SHAs back to mutable tags. Until then, any
workflow whose refs are not in the lock stays out of it rather than being
hand-written in, and `ci-health-sweep.yml` keeps the readable tag its lock entry
records.

*Four workflows are unlisted in the lock* (`codeql.yml`, `oikosbot.yml`,
`scorecard.yml`, `secret-scanner.yml` — `pages.yml` was the fifth and has been
removed; the temporary probe is also unlisted and is not counted as a gap because
it is about to be deleted). Measured again on the merge push: all four started on
`main` while absent from the lock — Secret Scanner succeeded, CodeQL and OikosBot
ran jobs and failed inside them, Scorecard created zero jobs for a reason
unrelated to the lock (its callee pin, above). So this is a coverage gap, not a
fault, and `scripts/check-lock-sync.sh` reports it as a NOTE and does not fail.
That calibration is deliberate and is now *tested* rather than merely asserted:
code mutant C5 in `tests/mutation-score-test.sh` replaces the gate's
`unlisted+=("$key")` with `fail_block "$key"` — the NOTE becomes a FAIL — and the
corpus kills it. It is killed only by a *benign* input (B5, a well-formed
workflow that simply is not listed), which is the concrete argument for why that
suite carries sixteen mutants that must NOT fire: a corpus of nothing but broken
fixtures would score a false-alarm mutant as undetected and let the gate drift
into crying wolf. Closing the gap itself needs the same re-arm trigger as the
lock.

*`gh actions-lock`'s extractor has a known blind spot.* It reads step-level
`uses:` only, so job-level reusable-workflow calls are invisible to it. This is
measured in both directions and recorded in `metadatastician/burble#224` ("fix(ci):
resynchronise actions.lock and gate it against recurrence", closed) under *The
tool's blind spot*: a job-level `standards@d135b05b` pin that disagreed with the
YAML's `@4d104d32` killed `mirror.yml` at startup yet appeared in neither
`--no-fix` nor `--verify-local` output and was not repaired by fix mode; and a
job-level ref that *was* correctly present in the lock was then reported `stale` —
"no uses: in this workflow references it" — about a ref literally on line 144 of
that file. The mechanism for the asymmetry is the step-level parse count: zero
step-level refs skips the stale check, nine step-level refs makes the unmatched
job-level entry look orphaned. This is exactly the class of error the estate's
YAML-POLICY rule Y-1 exists to end. The checkers in this repository read
job-level `uses:` correctly and are tested on it (`tests/yaml-reader-test.sh`, and
input mutant S14 plus the property test's job-level generator in the newer
suites), so the gap is in the generator, not in the gate. Its own README adds a
second limitation that matters for the deferred callers: "Workflows in the
lockfile cannot use local-path actions, these will be skipped for onboarding."

*Regenerating the lock rewrites workflows, and the rewrites must be discarded.*
Also measured in `metadatastician/burble#224`: `gh actions-lock` fix mode appended
duplicate management banners to 27 workflow files (one reached three banners) and
de-pinned two bare SHAs back to mutable tags (`dtolnay/rust-toolchain@02cb101e…` →
`@v1`). So Task 3's acceptance condition — regenerate, then confirm `git diff`
touches *only* `actions.lock` — is not a formality, it is the guard against a
tool that will happily un-pin this repository's workflows while fixing its lock.
When the tool becomes runnable here, regenerate in a scratch copy, take only the
lockfile, and re-run `scripts/check-lock-pins.sh` to prove no pin moved.

*The `check-workflows-parse.sh` gate has no parser in the authoring
environment.* That upstream script accepts `yq` or `ruby` and nothing else, and
the sandbox has neither (`yq` cannot be downloaded — same blocked host; `ruby`
cannot be installed — no root). Locally it therefore exits 1 with
`::error::no YAML parser available (yq or ruby)`, which is an *instrument
absence*, not a workflow defect. The properties it checks are verified here by a

itself is green (run `36361141993`, step 5). `tests/mutation-score-test.sh`

`hyperpolymath/standards` runs `lockfile-drift-detect.yml` on `cron: '20 7 * * 2'`
(Tuesday 07:20 UTC, after Dependabot's weekly window) and its header states the
fault is self-reinflicting — "60 of 60 sampled repos carry both a lockfile and a
Dependabot config, so the whole estate re-acquires this on every action bump".
But its enumeration step is `gh repo list hyperpolymath --limit 1000
--no-archived`, and every subsequent probe hardcodes
`repos/hyperpolymath/$r/...`. This repository is in the `metadatastician`
organisation, so it is outside that sweep's universe and always will be, however
many Tuesdays pass. That is why a four-day, four-run outage on this repository's
default branch produced no estate-level signal: the detector that exists to
produce exactly that signal is scoped to one organisation.

Widening it to both orgs is a small change in a repository this token cannot
write to, and it should be made — but it is worth being precise that it would
*not* have caught this incident, because the cadence has its own blind window.
The drift was introduced at 2026-09-23T11:10Z (a Wednesday) and repaired at
2026-09-28T00:09Z (a Monday). The Tuesday 07:20 runs either side of that interval
are 2026-09-22 and 2026-09-29: the first predates the fault, the second postdates
the fix. A weekly detector, at any scope, samples this outage zero times. The
only mechanism that ran inside the window was this repository's own *daily*
04:47 sweep — which was the thing that died. That is the strongest available
argument for `estate-sweep-watchdog.yml`, and it is an argument about cadence and
recursion, not about org scope: a detector cannot report its own absence, so
something else must notice the silence.
. *Two sweeps, one estate.* This repository's own `ci-health-sweep.yml` covers
`metadatastician`, so the two detectors are complementary in scope but not in
output shape. They should agree on it, so a drift reported by one is actionable
in the other's report.
. *Remediation cannot be dispatched from here.* Write access from the authoring
environment is confined to this repository, so the other repositories' drifted
locks cannot be repaired directly. The sweep's B-LOCKFILE class is therefore
report-only, by design, and the report is the deliverable.
