== What kind of component this is, and why that shapes the declaration

This repository ships no compiled program. It is shell gates, workflow YAML,
A2ML descriptors and AsciiDoc governance text. Most of the taxonomy's
categories are written for components with a build, a runtime and a wire
protocol; declaring them "present" here would be exactly the overclaiming that
`proven-tests-and-benches/TEST-NEEDS.adoc` warns is more expensive here than
anywhere else, because what this repository records is read as evidence in
other repositories.

So each category below is *REAL*, *THIN*, or *N/A with justification*, using the
three states that file defines and never collapsing the second into the first:

* *REAL* — a test that would fail if the property it names stopped holding.
* *THIN* — a genuine assertion, far weaker than the taxonomy's definition of
  that category. Not a template for other repositories.
* *N/A* — not implemented, with the justification §Scope requires.

== Category-by-category

[cols="1,1,3",options="header"]
|===
| Category | State | Evidence or justification

| 1. Unit
| REAL
| `tests/yaml-reader-test.sh` asserts `yaml_uses_in` behaviour by name: a
  job-level `uses:` is seen, a commented-out one is not, a sub-path ref
  normalises to `OWNER/REPO@REF`, a local `./…` ref is dropped.
  `tests/lock-pins-test.sh` asserts the determinate/indeterminate split per
  HTTP answer, and each exit code. `tests/ci-health-detect-test.sh` applies the
  same split to the sweep's repository-tree query (an empty repository is a
  determinate answer; a 403, a 404 and a different 409 are not), and
  `tests/ci-health-sweep-test.sh`, `tests/ci-health-sweep-errors-test.sh` (the
  unstubbed `sweep.sh` → `detect.sh` seam, cherry-picked from #52 and
  reconciled with #51) and `tests/estate-sweep-watchdog-test.sh` cover
  the refusal evidence and the watchdog's script, each against mutants of the
  code under test. Their fake `gh` runs the `--jq` filter it is given, because a
  stub that returns already-filtered text cannot see a broken filter.

| 2. Point-to-point
| N/A
| There is no pair of processes or services exchanging messages. The nearest
  boundary is gate ↔ GitHub API, and it is covered as a contract
  (see category 12) rather than as P2P.

| 3. End-to-end
| THIN
| `scripts/run-shell-test-suite.sh` exercises every gate end to end on a
  fixture repository, and the `CI` workflow runs the same suite against the
  real repository. There is no deployed system for a true E2E test to span.

| 4. Build
| N/A
| Nothing is built. There is no compiler, no artefact and no build graph, so a
  build test would have nothing to assert.

| 5. Execution / runtime
| REAL
| Every gate is executed, not merely parsed. The exit contract is asserted per
  case, and the ambiguity that makes this category worth having — "0" versus
  "never ran" — is the one this suite spends most of its checks on.

| 6. Reflexive
| REAL
| The gates read this repository's own artefacts: `scripts/check-lock-sync.sh`
  and `scripts/check-lock-pins.sh` are run against `.github/workflows/` by the
  `lock-sync-gate` workflow, and `scripts/kyaml-census.sh` censuses this
  repository's own YAML. A gate that only ever ran on fixtures is not evidence.

| 7. Lifecycle
| N/A
| No component here has start/stop/upgrade semantics.

| 8. Smoke
| REAL
| `scripts/check-workflows-parse.sh` sniffs the three shapes that kill a run
  before any job exists, and the `CI` workflow's environment step prints the
  tool versions so a green run cannot mean "the runner did nothing".

| 9. Property-based
| REAL
| `tests/ref-normalisation-property-test.sh`, added 2026-09-28. It *generates* a
  corpus of `uses:` refs — owners with and without dots, repos with dashes, refs
  as tags, full SHAs, short SHAs and branch names, refs with and without trailing
  `@`, plus exclusion prefixes in both bare and `@ref` form — and asserts eight
  properties of `scripts/lib/yaml.sh`'s `yaml_uses_in` over every generated
  member, rather than over hand-picked examples. Randomness is seeded and the
  seed is printed, so a failure reproduces; verified at exit 0 across seeds
  1/99/12345/20260928 at corpus sizes 25/40/80.
+
Two things make this REAL rather than a generator wearing the label. It carries
three *negative controls* — deliberately broken readers — and fails (exit 1) if
any of them is not caught, so "the property passed" cannot mean "the property was
never tested". And it earned its keep immediately: writing it exposed two genuine
bugs in the test's own reasoning that a hand-written fixture would not have
found, one being that `RANDOM` drawn inside a command substitution does not
advance the parent shell's sequence, so every array in the generator was silently
picking the same index and the corpus was far narrower than it looked.
+
Scope, stated so the claim is not over-read: the properties cover *ref
normalisation in the reader*, not the whole input space of the gates. The
hand-written fixtures in rows 1-8 are still the coverage for everything else.

| 10. Mutation
| REAL, with one declared hole
| `tests/mutation-score-test.sh`, added 2026-09-28, does mutation scoring in the
  textbook sense and in both directions. *Part A* mutates the **inputs**: 42
  corpus members over the lock-sync, lock-pins and workflow-parse fixtures, of
  which 26 must fire (a mutant that removes or inverts a defect the gate
  documents) and 16 must NOT (benign variants — a well-formed workflow that is
  merely unlisted, an entry that agrees, a pin that resolves). Detection 26/26,
  specificity 16/16. *Part B* mutates the **gate code itself**: six single-line
  mutations of `check-lock-sync.sh` and `check-lock-pins.sh`, each removing or
  inverting a documented decision, each run against the whole Part A corpus and
  killed only if some member's verdict changes. Code mutation score 6/6.
+
The benign half is not padding and Part B is why. The mutant that turns the
coverage NOTE into a FAIL is killed *only* by a benign input, so a corpus of
nothing but broken fixtures would score a false-alarm mutant as undetected and
let a gate drift into crying wolf unnoticed. Two of the six code mutants survived
the first corpus and were killed only by adding two new members — one whose only
defect is staleness, one whose only defect is ref format — which is the clearest
available evidence that the score measures the corpus and not the author's
confidence.
+
*Runner evidence, measured 2026-09-29.* On the `ubuntu-24.04` runner the five
parse mutants ARE scored (yq/ruby are present there): CI job `36551068185`,
step 4 (*Shell test suite*), reports detection 100.0% (**29/29**), specificity
100.0% (**18/18**), code mutation score 100.0% (**6/6**), zero NOT SCORED. The
local-home numbers below remain the recorded home-context measurement; the two
differ only by the five parse-family members, exactly as declared.
+
*The declared hole:* five parse-family mutants are reported **NOT SCORED** and
excluded from both denominators, because `scripts/check-workflows-parse.sh`
accepts only `yq` or `ruby` and the home context has neither. That is an
instrument absence, not a pass. Those five are scored on a runner, where the gate
has a parser; the suite prints which members were unscored so the gap is visible
in the output rather than buried in an average. On 2026-09-29 a runner run was
read — CI job `36551068185` step 4 — and it scored all five rather than skipping
them (29/29 detection, 18/18 specificity, 6/6 code, zero NOT SCORED), so the
hole now carries runner evidence instead of an open question. The label is
unchanged on purpose: the *home* context still cannot score them, and that is
what the label is about.
+
Every code mutant is anchored to a line that must exist verbatim in the gate; if
an anchor stops matching, the suite exits 2 ("no check performed") rather than
silently scoring a mutant that was never constructed.

| 11. Fuzz
| N/A
| No fuzzer is wired up. The obvious target — the YAML reader — is currently
  covered by delegating parsing to `yq`/`ruby`/PyYAML rather than to code of
  ours, so the fuzzable surface is third-party.

| 12. Contract / invariant
| REAL
| Three outcomes are enforced per gate — `0` ran and agreed, `1` ran and found
  whatever it looks for, `2` NO CHECK WAS PERFORMED — and both
  `tests/lock-sync-test.sh` and `tests/lock-pins-test.sh` assert that `2` is
  reachable exactly when the instrument is missing or the document will not
  load, and is never reported as a pass.

| 13. Regression
| REAL
| Each firing fixture is a committed specimen of a real incident: the
  job-level reusable `uses:` the estate's lockfile extractor went blind on; the
  tag-versus-SHA ref disagreement that refused this repository's own sweep runs
  (35957324128, 36096095736, 36218967182, 36295476367); the unauthorised
  OpenSSF Best Practices badge in `scripts/tests/test_readme_badges.py`.

| 14. Chaos / resilience
| N/A
| No long-running service to perturb.

| 15. Compatibility
| THIN
| One real instance is covered: `tests/lock-sync-test.sh` includes a flow-style
  YAML fixture, which is what caught this repository's first lock checker being
  a line reader. Portability across `yq` implementations is handled by
  detection rather than by tests, and `gawk`-only constructs have already
  caused one silent defect here — so this is THIN, and narrowing it is
  worthwhile work rather than a claim to defend.

| 16. Proof regression
| N/A
| This repository contains no proofs. The proof obligations it carries — the
  KYAML comment-preservation proof, rule Y-2's round-trip proof — belong to
  `hyperpolymath/standards` (issues #1021, #1022), and this repository's job is
  to consume their result, not to host them.

| 17. Type-safe
| N/A
| No type-safe language is used for testable code.

| 18. Coupling / drift-freedom
| REAL
| The strongest coverage here, and the category this repository exists for.
  `actions.lock` and the workflow YAML are two representations of one fact, and
  `scripts/check-lock-sync.sh` compares them in both directions, per workflow
  path, through a real parser. `scripts/check-lock-pins.sh` then re-asks GitHub
  whether every recorded pin still resolves.
|===

== Benchmarks

N/A, with justification. This repository makes no performance claim, and it has
no measured artefact whose regression would be meaningful. The only timing
concern is that the gates stay cheap enough to run on every pull request —
which is a CI budget, not a benchmark: a regression there shows up as a slow
check, not as a wrong result, and there is nothing to baseline.

== Aspects

The 14 aspects (Part II of the taxonomy) are assessed where they apply rather
than claimed wholesale:

* *Security* — applicable and partly covered. The gates that matter
  (`check-lock-pins.sh`, `check-lock-sync.sh`) are about supply-chain identity
  and fail closed on an unavailable instrument. `secret-scanner.yml` runs the
  estate scanner. Not covered: any assertion that the *scanner itself* is
  running rather than silently absent.
* *Error handling* — applicable and covered: three-outcome exit contracts and
  an explicit no-check message.
* *Simplicity, observability, documentation* — applicable; documentation is
  this file, `docs/governance/CI-CD-COVERAGE.adoc` and the gate headers.
* *Accessibility, i18n, performance, concurrency, data integrity, privacy,
  compliance* — N/A here, with the exception that *compliance* is the whole
  subject matter of this repository and is asserted by the workflows it
  dispatches, not by tests of this repository.

== Provenance: what was drawn from `proven-tests-and-benches`, and what was not

The taxonomy's §Provenance puts the Idris2 suite at
`hyperpolymath/proven-tests-and-benches` *first*, ahead of writing anything new.
That suite tests Idris2 code; this repository has none, so its corpus is N/A
and no test here is a copy of it. What is adopted is its *doctrine*, which is
binding on tests copied out of it and is followed here:

* harness and payload are separate, the harness must never fire on clean input,
  the payload must always fire on a member of its declared class
  (`docs/TEST-DOCTRINE.adoc`);
* every test carries a *silence fixture* and a *firing fixture*, and a test
  missing either is inadmissible;
* a crash is `2` — NO CHECK WAS PERFORMED — and never conflated with success.

If a future test here is written by adapting one of theirs, its `TEST-NEEDS`
entry must name the source and this section must be updated.
