= CI-Health Sweep — estate failure-class detector + auto-remediator
:toc: macro
:icons: font

Detects and auto-remediates the *infrastructure* CI failure classes that
repeatedly redden estate CI, diagnosed 2026-06-13 from `tma-mark2#52`. These
are **not** workflow-logic bugs — which is why earlier rounds of per-workflow
"surface fixes" had zero effect. The cause lived in account billing and repo
Actions settings.

toc::[]

== Failure classes

[cols="1,3,1",options="header"]
|===
| Class | Signature | Action

| `A-BILLING`
| A `failure` run whose job annotation reads _"the job was not started because
recent account payments have failed or your spending limit needs to be
increased"_. Blocks **all billable jobs** (private repos). Manifests on
code-scanning gates as _"waiting for results from CodeQL"_ (no result is ever
uploaded because the job never starts).
| **Report only** — owner clears it in GitHub → Settings → Billing & plans.

| `B-ALLOWLIST`
| `allowed_actions: selected` with `patterns_allowed` that does **not cover the
curated superset** — either empty (post-wipe: `hyperpolymath/*` absent) or
incomplete (has `hyperpolymath/*` but missing a third-party action, e.g.
`gitleaks`). Only GitHub-owned + verified-marketplace actions resolve, so every
uncovered `hyperpolymath/*` reusable + non-verified third-party action is blocked
at parse → `startup_failure` (zero jobs, no logs). Hits public repos too. The
required set mirrors `remediate.sh`'s PUT body exactly, so a fix converges to
zero-missing and this stops re-firing (idempotent).
| **Auto-fix** — PUT the curated superset (`action-superset.txt`), keep
`sha_pinning_required`.

| `B-STARTUPFAIL`
| An active workflow whose latest run is `startup_failure`. Historical failures
created before `CI_HEALTH_POLICY_EPOCH` do not keep the rolling issue open:
GitHub returns HTTP 403 when asked to rerun a zero-job startup failure, so rare
event-driven workflows may have no replacement run for months.
| **Report** — the API never exposes the reason; the **web-UI red banner does**
(it names the blocked action). Usually a missing allow-list pattern.

| `D-BURN`
| A workflow on bare `on: [push, pull_request]` — runs **twice** per PR commit
(branch push + PR synchronize).
| **Auto-fix** — open a PR scoping `push` to the default branch + adding
`concurrency: cancel-in-progress` (safe: these are read-only PR checks).
|===

== Components

* `detect.sh <repo>` — API-only classifier; emits TSV `repo CLASS SEV detail`.
* `remediate.sh <repo> <CLASS> <dry_run>` — applies B-ALLOWLIST (allow-list PUT)
  and D-BURN (idempotent signed PR). Guardrails: own repos only (skips
  forks/archived), `CI_HEALTH_DENYLIST`, idempotent, dry-run honoured.
* `sweep.sh` — estate driver: enumerate → detect → remediate (cap
  `MAX_BURN_PRS`) → upsert one rolling tracking issue.
* `baton-bridge.sh` — the complement to detect/sweep: where those *detect* that
  GitHub CI is blocked (`A-BILLING`/`B-ALLOWLIST`), this *runs the checks anyway*
  as Batons on **owned compute** (zero GitHub Actions minutes) via
  `metadatastician/bag-of-actions` (`mix bag.sweep`), then upserts a separate
  rolling tracking issue with the HMAC-attested verdicts. Invoke from a
  cron/systemd timer on the **.git-private-farm** — *never* from a GitHub Action
  (that would burn the minutes it exists to avoid and re-couple it to billing).
  Env: `BAG_OF_ACTIONS_DIR` (required), `MANIFEST`, `OWNER`, `ISSUE_REPO`, `DRY_RUN`.
  This is the piece that survives `A-BILLING`: a billing-blocked private repo's
  checks still get real verdicts, with no dependency on any GitHub run.
* `../../.github/workflows/ci-health-sweep.yml` — daily cron (04:47 UTC) +
  `workflow_dispatch` (manual defaults to dry-run).

== Operating notes / off-switch

* Needs `secrets.METADATASTICIAN_DISPATCH_PAT` with classic `repo`, `workflow`,
  and `admin:org` scopes. The allow-list is centrally enforced, so its PUT must
  target the organization; repository-level PUTs return HTTP 409.
* Scheduled runs remediate **live**; manual `workflow_dispatch` defaults to
  **dry-run**. Dry-runs write only the job summary and do not change the rolling
  issue. To pause auto-remediation, set the schedule run to dry-run or disable
  the workflow.
* Sweep gotchas baked in: drive off the API owner (never local dir names — some
  estate clones' `origin` ≠ dir name, e.g. `mirror-007` → `metadatastician/007`);
  PR-create always passes an explicit `base`; forks/archived/deleted remotes are
  skipped, not failed.
* New shared third-party action? Add it to `action-superset.txt`. Entries are
normalized and deduplicated before comparison and update.
* Organization allow-list health is detected/remediated once at its authority
scope. Repository scans cover runs, billing annotations, and workflow triggers.
  A successful organization allow-list update records `CI_HEALTH_POLICY_EPOCH`
  as an organization Actions variable. If it is unavailable, detection uses an
  explicit 25-hour fallback horizon (longer than the daily schedule interval).
* API failures are `E-INSTRUMENT` findings and abort a sweep. A partial scan is
never reported as a healthy estate.
* Exactly one failed answer is excused: an *empty repository*. GitHub answers
the tree query for a repository with no commits with `409 Git Repository is
empty.`, which is a fact about the repository (no commits, so no workflows)
rather than a failure to ask, so `detect.sh` prints `SKIP <repo> empty
repository` on stderr and reports nothing for it. Any other failed query --
403, 404, 422, 5xx, no network, or a 409 that says something else -- is still
`E-INSTRUMENT`. One empty repository refused the whole estate report on every
daily sweep from 2026-09-21, because it was not excused.
* A refused sweep (exit 2) names every target that failed and why: in the job
log, in the run summary, and as `::error` annotations. Annotations are plain
REST -- `gh api repos/OWNER/REPO/check-runs/<job-id>/annotations` -- so the cause
is readable even where the job log is not, and `estate-sweep-watchdog.yml`
quotes them in its comment on the stale-report issue. At most seven targets are
annotated individually (GitHub keeps ten per step, and the runner adds one of
its own); the log lists all of them.
* The tracking-issue body is capped at `MAX_ISSUE_BODY_BYTES` (default 60000):
GitHub refuses an issue body over 65,536 characters, and that refusal would
otherwise be the sweep's last act, after live remediation. A capped body is cut
on a line boundary and says so; the complete report is in the run summary.
* A complete finding-free sweep closes the rolling issue; a later real finding
opens a new report.

== B-LOCKFIX (opt-in lock-only repair)

For B-LOCKFILE, the sweep mirrors workflows and actions.lock through the API
without cloning or writing another repo. It runs both parser-first lock gates,
then runs the canonical generator on the runner. It includes the proposed lock
diff in the dry-run job summary. It will open at most `MAX_LOCKFIX_PRS` PRs only
when `ENABLE_LOCKFIX_PRS=true` is explicitly supplied on a manual dispatch with
`dry_run=false`; the daily schedule always leaves this class dry. PRs contain
the detector's drifted refs and failed run IDs. The stable repair branch and
existing open PR are reused. Workflow YAML changes are a standards#981 hazard:
report the diff and refuse mutation. B-BADPIN remains report-only: deciding
which commit matches a trailing version comment requires repository-owner review.
B-ACTOR remains owner-settings-only (org/repo Settings -> Actions); no repository
change applies. `lockfix.sh` itself exits 2 on API, parser, generator and token
failures, never success. What the sweep does with that exit depends on the mode:
in a scheduled (dry) sweep a failed proposal is a `::warning` annotation and an
`E-INSTRUMENT` line in the report's B-LOCKFIX section, and the report is still
published -- the proposal failed, the detection did not, and the B-LOCKFILE
finding is already in the report. A live run (`ENABLE_LOCKFIX_PRS=true`) can open
PRs in other repositories, so a failed repair check there still fails closed.
To prove in Actions: manually dispatch `dry_run=true`, `limit=3` after this
workflow reaches main, review the diff summary, then separately opt in to live
PRs. The authoring installation cannot dispatch this workflow (HTTP 403).

The first exercise of `lockfix.sh` against real repositories (2026-09-29, dry, the
generator stubbed because the extension cannot be installed where it was run)
found that it failed for *every* repository: its tree filter read
`.path | test(..) or .path==..`, and a pipe binds looser than `or`, so the
right-hand `.path` was evaluated on a string. It had never run for real because
the sweep never got past detection. `tests/ci-health-lockfix-test.sh` now runs the
filter it is given instead of stubbing the answer. What is still unproven is the
generator itself: no run of `gh actions-lock` through this pipeline has been read
back.
